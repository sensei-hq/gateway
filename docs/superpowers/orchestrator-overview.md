## 1. The shape — `goal → result`

The orchestrator is a **deterministic engine** (deterministic on *replay*, via the durable
journal — not because its steps are pure) that turns a **goal** into a **result**, emitting
a legible **event stream** the whole way so the run can be tracked, resumed, and (later)
paused for humans.

```
        goal (run input)
          │
          ▼
   ┌──────────────────┐   Slice B (planner selection): pick WHICH planner agent
   │ planner selector │   from the role‑classified library — deterministic rule
   │  (Rule | Llm)    │   OR a light reasoning call (journaled Pure effect).
   └──────────────────┘
          │  selected planner agent (role → reasoning chain via resolve_chain)
          ▼
   ┌──────────────────┐   Slice A: a journaled ReAct planner sub‑run under
   │  planner agent   │   "{expand}/__plan__". Pure discovery tools
   │  (drive_agent)   │   (list_agents/chains/skills/tools) + validate_plan.
   └──────────────────┘   Emits a right‑sized, self‑describing plan (native serde Graph).
          │  plan Graph (nodes carry NodePlan{label, description, needs})
          ▼
   ┌──────────────────┐   validate_dag + feasible() + caps → journal PlanExpanded
   │  splice (Expand) │   {node, subgraph} → reconstructed from journal on resume
   └──────────────────┘   (never re‑planned). This is the "memo for graph structure".
          │
          ▼
   ┌───────────────────────────────────────────────────────────┐
   │  executor / coordinator                                    │
   │  ready‑node scheduler over typed edges (Hard/Soft),        │
   │  cascade‑skip on failure; node kinds:                      │
   │    ModelCall · Agent · Map · Consolidate · Loop ·          │
   │    Subgraph · Branch · Expand · AwaitSignal · HumanGate    │
   │  on a DURABLE JOURNAL:                                     │
   │    effect classes Pure / Observation / Mutation;           │
   │    two‑phase + in‑doubt→reconcile for Mutations;           │
   │    effect_id memo ⇒ resume WITHOUT re‑spending tokens;     │
   │    version fence; snapshots; compaction; CAS blob split.   │
   └───────────────────────────────────────────────────────────┘
          │  events: OrchestratorHooks + journal
          │  (run/node/agent/context lifecycle, on_plan_expanded, RunPaused)
          ▼
        result (sink outputs)     ── + real‑time flow‑tracking UX / alerts / HITL
                                     built ON the event stream (consumers, not core)

   under everything: the GATEWAY (sensei‑gateway) — chains, fallback, health gates
   (breaker/cooldown/lockout), budget/quota, panels/consensus, credentials.
   config: the REGISTRY (agents/skills/tools + role→chain bindings) loaded via a
   pluggable ConfigSource, hot‑reloadable, tenant‑agnostic, config‑driven (no DB yet).
```

**Load‑bearing invariants (hold across every slice):**

- **No silent failures.** Every error takes exactly one explicit path (`fail | pause | replan | retry | in_doubt→reconcile`), journaled + surfaced.
- **Deterministic replay / no re‑spend.** A completed effect is memoized by structural `effect_id` + input‑hash; resume replays it with zero gateway calls. Impure steps (LLM calls, the planner, an LLM judge) are made replay‑safe by **journaling their output once**, not by being pure functions.
- **Tenant‑agnostic core.** The gateway *and* orchestrator cores have no tenant concept; multi‑tenancy is a wrapper (one entity per tenant).
- **Config‑driven; persistence is opt‑in (SP‑DATA COMPLETE).** Everything still runs on in‑memory config (`CatalogConfig → assemble → GatewayConfig`; `ConfigSource → Registry`), and durable persistence remains a **layer behind backend‑agnostic seams** rather than a core dependency: **`PostgresJournal`/`ContentStore`/`ContextStore`** (s1) give cross‑process durable resume, **`PostgresConfigSource` + `config_versions`** (s2) make the config generation in the fence durable, the **durable scheduler** (s3) re‑arms a paused run at its `resume_after`, **`torii`** (s4) is the operator control plane, and the **per‑run token budget** (s5) bounds what a run may spend. All are `postgres`‑feature‑gated or opt‑in ⇒ unwired, the library is byte‑identical.
- **Opt‑in policy, light core.** Blackboard/hooks/CAS/reconcilers/planner are injected; unwired ⇒ the light path is byte‑identical.

## 2. The complexity ladder (planner right‑sizing)

The planner emits the **lowest tier that satisfies the goal** — a simple atomic task stays a
single‑level list; nesting/fan‑out/branching/runtime‑expansion appear only when the task
demonstrably needs them.

| Tier | Shape | Node kinds |
|---|---|---|
| 1 | single agent, single task | one `Agent` node (+ `NodePlan`) |
| 2 | parallel multi‑agent + consolidation | `Map{Agent bodies}` → `Consolidate{Agent}` |
| 3 | conditional · nested · iterative | `Branch` · `Subgraph` · `Loop` |
| 4 | runtime sub‑planning | `Expand` (recursive; caps‑bounded) |

Consensus/voting is **not** a tier of its own — it's `Map{blind voters} → Consolidate{evaluator}`
(bias isolation is already guaranteed: Map children run isolated and can't read siblings).

## 3. Decision log (asked → confirmed)

Grouped by phase. Each line is a confirmed decision; the per‑slice spec (§4 index) is canonical.

### SP‑0 — gateway health gates (merged; on `main` via PR #45)
- **Composable policy pipeline**, not subclasses: `AdmissionGate` chain + `RoutingStrategy` + `HealthRecorder` + `SelectionObserver`, composed via a builder.
- **Classification at the adapter boundary** (status/Retry‑After/body preserved); one pure `classify()` drives both in‑walk demote‑to‑tier and next‑request lockout. Deliberate `403 ≠ Authentication`.
- **Tenant‑agnostic health:** the gateway *announces* (`on_lockout`), the **caller persists** (`apply_lockout`/`clear_lockout`); the gateway never persists.
- **Durable pause vocabulary:** `GatewayError::AllGated{resume_after, skipped, human_action}` — timed ⇒ wall‑clock pause; all‑terminal ⇒ fail‑fast with a `HumanAction` hint. Invariant: `AllGated ⟺ every candidate gated AND none hard‑failed`.
- **`ResilienceConfig` at construction** (not a hot‑swappable `GatewayConfig` field), bounded eviction (expired‑only), deterministic keyed jitter (synthetic backoff only; default off).

### SP‑CAT + reference chains (merged)
- Free‑tier **catalog metadata** as optional `ModelConfig.catalog` (kernel, backward‑compatible); **tiers** = curated members ∪ attribute‑derived predicate (deterministic sorted); **pure `catalog::assemble() → GatewayConfig`** (tier‑ref chains → concrete `FallbackChainConfig`s; SP‑0 selection untouched). `cost_band` derived‑from‑pricing (override wins); `Headroom`/`LeastUsed` stub→`Priority` (need live usage).
- Portable **reference tiers + chains** (`research.bulk`, `plan.frontier`, `code.exec`) ship as editable reference data; chains stay user‑owned.
- **⚠️ USER DIRECTIVE:** the app stays **config‑driven, no persistence** — SP‑DATA is a separate, held‑off layer.

### SP‑1 — durable walking skeleton (merged)
- **slice 1 (spine):** 3 crates (`orchestrator-core` zero‑I/O · `orchestrator` engine · `orchestrator-store`). Linear Pure `ModelCall` graph; structural `effect_id(parent_path ‖ loop_iteration ‖ local_index)`; resume/fold memo ⇒ **no token re‑spend**; version fence; terminal‑guard.
- **slice 2 (agent runtime):** in‑memory `Registry` (frontmatter subset) + `NodeKind::Agent`; ReAct loop where **each turn is a Pure `ModelCall` effect** and each Pure tool call a Pure effect ⇒ resume‑without‑re‑spend extends *into* the loop; **two‑registry split** (core specs vs executable `ToolRegistry`); per‑turn window budget (halt‑loud, never truncate) — **both halves of that last clause are now gone: SP‑7a deleted the chain‑minimum halt (the gateway's `ContextWindowGate` asks per candidate) and SP‑7b replaced the refusal with a journaled, disclosed CUT.** Left here as the record of what slice 2 shipped; §5's SP‑7 entry is the current behaviour.
- **slice 3 (fan‑out · blackboard · CAS):** typed edges `EdgeKind{Hard,Soft}` + `validate_dag`; **ready‑node scheduler**; `Map` (internal bounded fan‑out) + `Consolidate` (+ `Aggregation::Quorum`, `min_viable` starve‑guard); **cascade‑skip on hard edges only** (soft‑dependents still run; failure suppresses `RunCompleted`); CAS split‑on‑output (ref‑or‑inline, lazy materialize); round snapshots (out‑of‑band); compaction primitive.
- **slice 4 (effects):** `Pure / Observation / Mutation` dispatched by `ToolSpec.effect_class`; Observation = memoize‑with‑TTL+provenance; Mutation = **two‑phase `EffectIntent`→`EffectRecorded`** + **`in_doubt→reconcile`** (`Confirmed | NotApplied | Indeterminate→RunPaused`); pause propagates out of a Map child loud (`MapChildPaused`).
- **blackboard wiring:** executor‑managed; a node publishes its output to `Run/node.id`; an Agent reads its **Hard deps' outputs only** (determinism: hard deps are completed+published+stable before the dependent runs). Resume rehydrates from journaled `ContextWrite`s.
- **Loop:** `NodeKind::Loop{body, input, gate, max_iters}`; **pure `LoopGate`** (no gate journaling); refine thread feeds prior text forward; cap‑without‑stop ⇒ best‑effort `{converged:false}`, never a bare fail.
- **Hooks:** `OrchestratorHooks` (no‑op defaults) fired from inside `append` ⇒ can't‑miss **and replay‑suppressed for free**; opt‑in ⇒ byte‑identical.
- **quota→pause:** pure `classify_gateway_error` — only `AllGated{resume_after:Some}` pauses (durable `RunPaused`); everything else fails. **Completes the SP‑1 skeleton.**

### SP‑2 — registry (merged; closes the registry phase)
- **slice 1 (ConfigSource):** `ConfigSource` is *the* extension trait (async, domain objects, no serialization in the contract); `Registry::from_config` is the single assembly point (dup names fail loud); `FilesystemConfigSource` isolates all md/JSON parsing.
- **slice 2 (role→chain):** `resolve_chain(agent, phase)` = per‑phase `chains[phase]` → explicit `chain` → `(area,kind)` binding → loud. **`(area,kind)` role table** with `chain` as optional override; **phase is a node attribute** (`Agent{…, phase}`), not a mid‑loop transition; **multi‑tenancy by composition** (per‑tenant Executor/Gateway/ConfigSource; no `tenant_id` in core).
- **slice 3 (tool permissions):** two‑sided **declaration** model (`ToolSpec.permissions` needs vs `AgentDefinition.grants`); `covers()` predicate; secure‑default deny/empty; central auditable `grants.json`; **runtime enforcement deferred to SP‑4** (declarations only; inert this slice).
- **slice 4 (activation policy, Q4):** **definition‑level** activation (`Activation{Always | OnKeywords}`); `assemble_prompt(…, query)` includes a skill/tool only when active; **query = node input, matched once per run** (determinism); planner‑selected & retrieval‑ranked activation **deferred** (planner‑selected → SP‑3; semantic → SP‑7). Orthogonal to permissions (security boundary) vs activation (prompt disclosure).
- **slice 5 (hot‑reload):** `RegistryHandle` (swappable `Arc<Registry>` + monotonic generation); `reload` is **atomic, validated, last‑good** (load+validate before the write lock); per‑run **pin** at entry; config generation folded into the fence version (`"{base}#cfg{gen}"`) ⇒ one config generation per run.

### SP‑3 — hierarchical executor (COMPLETE on `develop`)
- **slice 1 (Subgraph):** `NodeKind::Subgraph{graph}` driven as a nested DAG in the **same run** via `namespace_graph` + `drive`; output = **sink‑outputs map**; recursive `validate_dag`; **`max_depth`** cap. Fixed two reuse bugs: `finalize_run` moved out of `drive` (no premature `RunCompleted`); `ModelCall` effect‑id node‑scoped (no nested/outer collision).
- **slice 2 (Branch):** `NodeKind::Branch{on, arms, default}` + pure `BranchCond`; runs the first matching arm as a nested graph; **decision is pure over `on`'s memoized output ⇒ no branch journaling**; `on` must be a **Hard dep**. Lesson: any node kind referencing a sibling id (`Consolidate.over`, `Branch.on`) **must** be rewritten in `namespace_graph`.
- **slice 3 (PlanDelta / Expand):** `NodeKind::Expand{input}` + injected **`Planner` trait**; the produced graph is **journaled as `PlanExpanded` and reconstructed on resume — never re‑planned** ("memo for graph structure"). **`drive_nested`** extracted (3rd caller; retires Subgraph/Branch duplication). **Two‑tier failure:** planner/invalid‑plan/no‑planner → node `Failed`; cap breach → hard `Err`. **Caps** `max_expansions`/`max_nodes` seeded from the journal so they **span resume**.
- **slice 4A (planner agent):** `PlannerRef::{Agent, Injected}`; a **journaled ReAct planner sub‑run** at `"{expand}/__plan__"` via `drive_agent` → `PlannedGraph{graph, node_plans}`; pure `feasible()`/`parse_plan()`/`validate_plan` gate; `NodePlan{label, description, needs}` carried as the `PlanExpanded.node_plans` **side‑map**; Pure discovery tools; `on_plan_expanded` hook. Review caught a swallowed `DeterminismViolation` (→ `?`‑propagate) and a **feasibility gap** on nested `MapBody::Agent` refs (→ `check_agent_refs` recurses into Map/Consolidate/Loop bodies).
- **slice 4B (planner selector):** `PlannerRef::Select` + injected **`PlannerSelector`** (`RulePlannerSelector` pure + `LlmPlannerSelector` one‑call capability menu `name (area/kind)`); picks a **`planning`‑area** agent for the goal; **`PlannerSelected{node, agent}` journaled + folded** (resume reuses the pick) + `on_planner_selected` hook; anti‑hallucination `∉candidates`; extracted `drive_planner_agent`.
- **slice 5 (coordinator + loops‑of‑graphs) — CLOSES SP‑3:** `Loop.body: MapBody→**LoopBody**{ModelCall, Agent, Subgraph, Expand}` + `gate: LoopGate→**GateSpec**{Pure, Agent}`. **Subgraph body** = fresh re‑run each iteration (gate decides stop); **Expand body** = plan+execute+**refine** (thread the iteration output into the next planning input — the coordinator core); **gate‑agent** at reserved `"{loop}/{i}/__gate__"` (journaled answer → pure `stop_when`; this is the **graph‑body** convergence path, since a pure gate can't match a nested sink map — pure gate = leaf convergence). **`drive_expand_with`** extracted (shared by `run_expand` + Loop‑Expand); the run‑scoped caps **compose per‑iteration**. **The coordinator** = `Loop{ body: Expand{planner}, gate: Agent{…} }` — plan→execute→gate→replan, native + resume‑safe. Final whole‑slice review caught + fixed **`__gate__` not reserved in `feasible`** (an untrusted planner could emit a `__gate__` node → journal collision → resume `DeterminismViolation`) and an **unproven Expand refine** (input‑ignoring test planners) → added an input‑sensitive refine test.

### Planner brainstorm — SP‑3 slice 4 (design agreed 2026‑08‑13; **BUILT** — slices 4A + 4B merged)
*Split into **Slice A** (core + journaled planner) and **Slice B** (selector); the confirmed decisions below are recorded as the design rationale.*
- **Determinism framing (confirmed):** the engine is deterministic on *replay* (journal), not because the planner/consensus are pure. The planner and any LLM judge are non‑deterministic computations made replay‑safe by journaling their output.
- **Consensus (clarified):** a **blind, independent fan‑out + evaluator** (voters don't share context / see each other's answers — bias isolation). Already expressible as `Map{voters} → Consolidate{evaluator}` (Map guarantees isolation); a pure evaluator is deterministic, an LLM judge is journaled‑replay‑safe. **Not** the planner engine; a first‑class `Consensus`/`Vote` node or wiring the gateway's `execute_consensus` is optional/future.
- **Plan palette (confirmed):** **FULL** — the planner may emit every node kind incl. recursive `Expand`; the slice‑3 caps are the only backstop.
- **Planner mechanism (confirmed):** **ReAct planner with discovery tools** (`list_agents/chains/skills/tools` + `validate_plan`), grounded in what actually exists.
- **Deliberation durability (confirmed):** **journaled planner sub‑run** — `run_expand` drives the planner via `drive_agent` under `"{expand}/__plan__"`; ReAct turns are Pure effects ⇒ a mid‑plan crash **replays turns from the memo**. `PlannerRef::{Agent, Injected}` selects trait‑vs‑agent.
- **Self‑describing plan (confirmed):** `NodePlan{label, description, needs}` carried as a journaled **side‑map** `PlanExpanded.node_plans: HashMap<NodeId, NodePlan>` (keyed by local node id) — **not** a `Node` field (avoids a 94‑literal churn; core `Node`/`Graph` unchanged). `needs{skills,tools,agents,self_discover}` doubles as **planner‑selected activation** (the SP‑2 Q4 deferral); surfaced with the graph via `on_plan_expanded` so the UX/tracking see labels.
- **Right‑sizing (confirmed):** planner emits the lowest tier of the ladder (§2); flat single‑Agent for simple tasks.
- **Agent selection (confirmed):** a **role‑classified agent library** (= the SP‑2 registry) + a **selector** that picks the planner — **deterministic rule OR light‑LLM** (journaled) — → **Slice B**.
- **Decomposition (confirmed):** Slice A = `NodePlan` schema + `feasible()` + `validate_plan` primitive + journaled planner agent + discovery tools + `on_plan_expanded` hook; Slice B = `PlannerSelector` (Rule + Llm) + `PlannerRef::Select`.
- **Observability (confirmed):** the journal + `OrchestratorHooks` + `NodePlan` are the **flow‑tracking feed**; add the (previously‑deferred) **`on_plan_expanded`** hook so a UX gets the labeled plan in real time. **HITL** (`HumanGate`/`AwaitSignal` = SP‑6) and **human‑as‑Agent** are designed‑for consumers on the existing pause/resume + event substrate — SP‑6 s1 landed `AwaitSignal` on that substrate, but **fires no hook for `SignalAwaited`/`SignalReceived`** (deferred, §5), so a live UX still learns of a human gate only by polling `torii run list-paused`.
- **Feasibility (confirmed default):** checks registry‑resolvable refs (agents/skills/tools) + structure (`validate_dag`, distinct/non‑reserved ids, `"__plan__"` reserved) + caps; **chain‑existence is best‑effort in Slice A** (bad chain → runtime gateway error → node `Failed`).

### SP‑4 — permission/effect ENFORCEMENT + isolation (in progress on `develop`)
- **slice 1 (tool permission enforcement):** turns the inert SP‑2‑s3 `Permissions`/`covers()` **declarations** into runtime **authorization**. The gate lives at the single chokepoint `execute_tool_effect` (all Pure/Observation/Mutation calls route through it): a call is denied unless `tool ∈ agent.tools` AND `agent.grants[tool].covers(tool.required(args))`. **`Tool::required(&self,args)->Permissions`** (default = static `spec().permissions`) reports a call's **concrete** needs, so the grant is a *runtime ceiling* (narrower than the tool's max surface) — the load‑time full‑surface `validate` check is **dropped** (D3; a narrow grant is now legal, enforced per‑call). `covers()` hardened: **component‑aware paths** (`/work` ⊄ `/workspace‑secret`, empty‑path reject, `..` reject) + **host wildcards** (`*.example.com`). A denial is recorded as a **Pure `EffectRecorded`** (no tool run; **no `EffectIntent`** for a Mutation) and fed back to the agent as a **terse** tool‑result error (never enumerates the grant → confused‑deputy defense) ⇒ a resume replays the denial from the memo, tool never re‑invoked (mutation‑verified `effect_recorded_count==1`). **Trust boundary (stated):** this AUTHORIZES (stops the agent invoking un‑granted tools / an honest tool being *asked* to exceed the grant); it does NOT CONFINE a tool that under‑reports its `required` — runtime confinement + resource‑cap *killing* = the sandbox (slice 4). Whole‑slice review READY‑TO‑PUSH (single verified chokepoint; in‑doubt reconcile on resume re‑runs the gate ⇒ a revoked grant denies rather than re‑runs the side effect; additive — empty‑permission tools byte‑identical). **NEXT SP‑4 slices (provisional): s2 secret redaction · s3 workspace isolation · s4 sandbox + cred broker · s5 exactly‑once hardening.**
- **slice 2 (secret redaction):** scrub secrets from effect **outputs** before they are journaled or fed back to the agent, via a pure injected **`Redactor`** (`orchestrator-core`) — default **`PatternRedactor`** (curated secret‑shape patterns → `[REDACTED]`: OpenAI `sk‑`/`sk‑proj‑`, Anthropic, AWS, GitHub `gh[opsru]_`/`github_pat_`, Slack, Google, Stripe `sk_live_`, Bearer, PEM, `key=value` assignments; ReDoS‑safe `regex` automata). Opt‑in `Executor::with_redactor` (default off ⇒ **byte‑identical**). **The determinism crux:** redact **at production, before BOTH journaling and the agent/downstream‑return** (a journal‑only scrub would replay `[REDACTED]` on resume while live fed the secret → spurious `DeterminismViolation`); the redactor is **pure** ⇒ live == journaled == replayed, memo replays the redacted value. So the model never sees the secret (anti‑exfiltration) — credential *use* stays the sandbox/broker (s4). **Leaf sites:** the tool result (`record_tool_effect`) + **every model‑output producer via a single shared `model_output` chokepoint** (`dispatch_model_turn` [+`tool_calls` intact] · `ModelCall` node · `Map`‑item · `Consolidate`) + **the reconcile‑in‑doubt `Confirmed` output**; CAS blobs (`split_output` runs *after* redaction), `Map`/`Consolidate` sink maps, and `ContextWrite` inherit transitively. **Two plaintext leaks the reviews caught + fixed:** the Task‑2 review found redaction hit only 1 of 4 model‑output producers (→ `model_output` chokepoint); the **whole‑slice review found the reconcile‑in‑doubt `Confirmed` path** journaled+fed‑back a reconciler's Mutation output **unredacted** — a *silent* durable plaintext write on resume (no memo to fence) — fixed by redacting the Confirmed output (mutation‑verified). **Best‑effort by shape** (§4.4 — misses novel formats; precise known‑value/vault redaction is a future `Redactor` impl). **Carry‑forward:** reversible tokenization/crypto‑shred (SP‑DATA); entropy heuristic; redactor‑version in the fence; input‑side/plan‑structure redaction; a `leak_exec` test‑helper cleanup.
- **slice 5 (exactly-once — idempotency-key core):** make the SP-1-s4 two-phase Mutation mechanism deliver **real provider-side exactly-once** by closing the one gap — the `idempotency_key` was journaled but never reached the tool, so a real tool couldn't send it to an external API to dedupe on. **Additive `Tool` seams:** `call_ctx(args, &ToolContext{idempotency_key, effect_id})` (default → `call`) + `idempotency_key(args) -> Option<String>` (author override, default `None` → structural `sha256(effect_id|args_hash)`); `ToolRegistry::{execute_ctx, idempotency_key_of}`. **Executor:** `mutation_tool_effect` computes the **effective** key (author else structural), journals it in the `EffectIntent`, threads it to the tool via `call_ctx` (the tool sends the SAME key it journaled to its provider); `reconcile_in_doubt` **READS the journaled key** from `fold.intents` (changed `HashSet<EffectId>`→`HashMap<EffectId,String>`, D3) instead of recomputing — so on in-doubt resume the provider is queried by the exact key used at execution (robust for author keys). **Exactly-once proven both ways** (demo keyed "external system" store + `StatusQueryReconciler`): Confirmed-by-key records without re-invoking the tool (a raw `invocations` counter — distinct from the dedup-aware `calls` — pins "tool NOT re-invoked on resume"); NotApplied runs the effect once under the standing Intent (no 2nd Intent); an author-keyed variant proves `bk-77` journaled + reconcile-queried-by-it. **Absent provider → `Indeterminate` → `RunPaused`** (R3 mandatory-human-reconciliation, unchanged). **Additive:** default tools journal the structural key exactly as before, reconcile reads that same key ⇒ byte-identical (the whole SP-1-s4 in-doubt suite green); `ToolRegistry::execute` gated `#[cfg(test)]` (production dispatches only via `execute_ctx` — a call_ctx-bypass footgun retired). **Trust boundary:** makes exactly-once ACHIEVABLE (mechanism + key); true exactly-once still needs the provider to honor the key. **Carry-forward:** saga/compensation; retry-under-key; real provider API integrations; richer `ToolContext`; author-key purity/version fence.
- **credential broker (ephemeral secret injection):** lets a tool authenticate to an external system **without the secret ever touching the model or the durable journal** — completes the SP-4 arc (s1 *authorizes*, s2 *redacts*, s5 *exactly-once*, the broker *provides the credential out-of-band*). **`Secret`** (`orchestrator-core`, `Zeroizing<String>`, `[REDACTED]` Debug incl. `{:#?}`, no `Clone`, single audited `expose()`) + injected async **`CredentialBroker` trait** (`resolve(cred_ref) -> Option<Secret>`; demo `StaticCredentialBroker`; a real impl wraps `vault::Vault`). A tool **declares** its refs on `ToolSpec.credentials: Vec<String>` (`#[serde(default)]`) — declarative alongside s1 `permissions`; forced by the **async broker / sync `call_ctx` boundary** (the executor must resolve *before* the sync call). `record_tool_effect` resolves each declared ref via `Executor::with_credential_broker` (default none) and injects the `Secret`s into `ToolContext.credentials: Arc<HashMap<String,Secret>>` (Arc ⇒ clones share one store, zero plaintext copies) — **ephemeral: never journaled / hashed (`input_hash` is over `args`, computed before resolve) / re-injected on a memoized resume** (a completed tool replays its journaled secret-free output; - **slice 5 (per-run token budget) — CLOSES SP-DATA:** a cap set at submit, enforced by the executor, and **durably ledgered** so it survives a cross-process resume; exhaustion pauses the run for an operator to raise it. **The crux — the journal IS the ledger.** Spend rides on **`EffectRecorded{usage}`**, the cap on **`RunStarted{budget}`**, and a new **`BudgetRaised{new_total_tokens}`** moves it — all `#[serde(default)]`-additive, so `FORMAT_VERSION` stays **1** (verified by deserializing a genuine pre-slice event, not assumed). Nothing else could deliver the property this stack needs: **an in-memory counter restarts at zero on every resume**, so each wake would let the run spend its ENTIRE cap again, unbounded across wakes — the exact bug class SP-DATA-1/2/3 exist to prevent. Usage rides INSIDE `EffectRecorded` rather than in a sibling `SpendRecorded` event because that would be **two appends per model call**, and a crash between them leaves a torn pair (spend without its effect, or an effect whose spend vanished); one atomic append cannot tear. A separate `run_spend` table was rejected for the reason it always is here — two sources of truth for one fact, with no principled answer when they disagree. **The fold keys by EFFECT ID, never by event, and the reason is concrete rather than hygienic:** the two-phase Mutation path can append a **second** `EffectRecorded` for one `effect_id` (an in-doubt `Confirmed` reconcile), so a naive sum over the event stream **double-counts that spend on every resume**, the overcount compounding with each wake; an `insert` keyed by id absorbs the duplicate and makes the fold idempotent by construction (mutation-verified — sum a per-event `Vec` instead and the guard test fails 300 vs 150). **ONE dispatch chokepoint, not four:** there were four `gateway.execute()` sites and no shared helper, and this codebase has already been bitten by exactly that shape — **SP-4 s2's review found the secret redactor wired into only 1 of the 4 model-output producers**. Here the failure would be worse: an ungated path spends real tokens past the operator's cap, silently. The **Mediums**: a decision past the gate's deadline is now refused up front (deterministic, not a race — the deadline is durable and `now` is a parameter — narrowing a window the executor still closes); a decision a RACING worker folded and completed is reported a **SUCCESS**, not `not queued` (the same inversion-on-the-most-successful-path `run signal` shipped); `gate decide`'s echoed option name was unguarded (author free text from a `run submit` file or an untrusted `Expand` planner's subgraph, and `validate_dag` checks options only for non-emptiness, uniqueness and a reachable outcome — never content or length) and its note unbounded; and the nondeterministic validation message above. **AC12, the cross-process e2e:** submit → durable pause → `list-paused` names the node and its menu → `gate decide` in process B → a FRESH `worker serve --once` completes it, over Docker `postgres:16`. It is `DATABASE_URL`-guarded and **returns early without one, so it is counted among the PASSING tests having exercised nothing** — a raw-stderr `SKIP` line is the only signal, and the green total says nothing about whether it ran. **Suite: 1427 → 1505 passed / 0 failed / 7 ignored**, green with and without `DATABASE_URL`. **A re-review OF THE REVIEW FIXES then found seven more — defects introduced while fixing defects, three of them HIGH, all in `torii`.** All three HIGHs were in `gate decide`'s post-append classification: (a) the `(other, true)` arm was imported wholesale from `cmd::run::signal`, where its premise HOLDS (`run_await_signal` never fails a node BECAUSE of a payload) but where `HumanGate` breaks it — `GateOutcome::Fail` makes a `NodeFailed` the *requested* outcome of a decision that WAS read — so a `gate reject` a racing worker folded and honoured reported exit 2 and *"a drive … would not have seen it"*, every clause false; `chosen.outcome == Fail` is NOT a sufficient discriminator, because `wait_or_expire` takes `Expired` before any decision is read and a deadline firing in the same window lands identically, so the journaled `fail_gate` MESSAGE at the terminal seq is what separates them. (b) **Both "not read" arms were asserted by nothing** — collapsing the whole block to `if at.is_some() { ok("decided") }` left 192 tests green, the identical lie the review had just removed one arm earlier. (c) The post-append `unread` closure interpolated a journal-backend fault RAW: a `postgres://` password, a newline forging a pastable run row and an ANSI escape all reached stdout, from a message `PostgresJournal::load` builds out of both `sqlx::Error` and `serde_json::Error` — the guard (`render::safe_reason`) already existed and was already proven on the same error class by `list-paused`; **the same gap pre-existed in `cmd::run::signal` and was fixed with it.** Two Mediums were guards applied to one value but not its sibling: `--as` was unbounded on the very row `--note` is capped on (a 131 KB actor accepted, exit 0, journaled — 32x the sibling's cap, and the executor interpolates it into the rejection `NodeFailed` every later drive re-emits), and the success line collapsed the option name without capping it (324 chars with an ellipsis on the refusal path against **5065 with none** on the path an operator always reaches). Two doc Mediums: this section and `CHECKPOINT.md` still prescribed a merge that had already happened, and spec §6.1 claimed the answer-read position was *"the one thing the two kinds do differently"* when there are **two** — `run_await_signal` also re-checks the clock after journaling a FRESH deadline, so a gate given a nanosecond pauses on an instant already behind it (one extra scheduler wake) instead of failing in the same execution. Both now recorded, because s3 is the third waiting kind and inherits both. **Deferred / carry-forward:** **authorization** (who MAY decide what — its own slice, arguably its own SP); a distinct **`RunStatus::Rejected`** (a business rejection and a dead provider are indistinguishable BY STATUS today, distinguishable only by the reason text, which matters to anything filtering on status — a script, or the terminal allowlist `count_terminal_before`/`prune_terminal` uses; a real status would reach both store impls, the dbd `CHECK` constraint and torii's rendering, which would stop s2 being a layer over s1); **non-CLI delivery** and **N-of-M approval**, inherited from s1; **no `OrchestratorHooks` callback fires for either gate event** (both fall through the hook-dispatch catch-all, matching s1's signal events — not a regression, but a HITL pause is precisely the event a live flow-tracking UX would want); and **`--note-file`** — not added, since a rejection reason is prose rather than a credential channel, but `--note`/`--reason` are argv, so the `ps`/shell-history/CI exposure that motivated `--payload-file` does apply and is an accepted risk.
- **slice 3 (human-as-Agent — a role answered by a person):** the third waiting kind — s3 wrote "and last", and s4's loop gate is the fourth — and the first that is a **REGISTRY fact rather than a graph one**. `AgentBacking::{Model, Human{timeout}}` on `AgentDefinition`, `#[serde(default)] + #[default] Model`, so every existing agent md, every `config_agents` jsonb row and every registry test is byte-identical. Authored as `backed_by: human` + `timeout: 48h` in frontmatter — both LOUD rather than lenient, because `backed_by: huamn` silently read as `Model` gives a config that LOOKS like a person is in the loop while the run quietly spends tokens, and a `timeout` on a model agent lets an author believe they set an SLA that is inert. Without the frontmatter keys `torii config push` (replace-all, diffed through `AgentDefinition`) would also silently rewrite a `Human` row back to `Model`, showing the operator only `changed: agent <name>`. **`Registry::validate` must SKIP its chain-resolvability requirement for a human backing** — the compiler cannot catch that, and without it every human-backed agent is rejected at config load before a node ever runs. **The short-circuit sits AFTER prompt assembly and BEFORE `resolve_chain`**, which is what makes zero token spend STRUCTURAL rather than measured: no chain is resolved, no gateway is touched, and `resolve_chain` would in fact FAIL for the common shape of such a role (`chain: None`, no `(area,kind)` binding). Two new journal variants (`AgentAwaited{node,deadline,prompt}` · `AgentAnswered{node,text,actor}`) ⇒ **`FORMAT_VERSION` stays 1**; answers fold LAST-wins (an operator can correct one before the run resumes), prompts FIRST-wins (the human was asked THIS question), and the `AgentAwaited` arm also writes the SHARED `deadlines` map every waiting kind reads. Output is `{"text","actor"}` under the **same `"text"` key a model-backed agent produces**, so an unmodified `BranchCond::TextContains` consumes a human's answer without knowing it was human. **The answer is read BEFORE expiry — a deliberate divergence from s2**: a gate decision is an APPROVAL and a late one must not approve an expired gate, but an agent's answer is WORK PRODUCT, so there is nothing to self-approve and discarding an in-time answer because a worker was down punishes the human for infrastructure they had no part in; the divergence is bounded by `gate_precheck` running FIRST, so a fired expiry is still terminal. The waiting machinery is SHARED with both siblings (`gate_precheck_by_id`/`wait_or_expire_by_id` — the `_by_id` forms exist because this node is driven from `drive_agent`, which holds only a `NodeId`). **Operator surface:** `torii run agent answer <run> --node <id> (--text|--text-file) [--as who]` with the three-way cross-refusal (`run signal` → `AwaitSignal`, `run gate decide` → `HumanGate`, each naming the verb that WOULD work), and `run list-paused` rendering the question. **Whole-slice review — the five that mattered.** (1) **§5.5's top-level rule was keyed on the CALLER, not the node's POSITION.** `run_node`'s `Agent` arm passed a hardcoded `true`, but `run_loop`→`drive_nested`→`drive`→`run_node`, so wrapping the same agent in a one-node `Subgraph` body declared it top-level and delivered "a human re-answers every `Loop` iteration" — one of the four features the refusal exists to prevent — with two real journaled questions at `lp/0/review` and `lp/1/review`, and authorable by an untrusted `Expand` planner. `drive` now carries a `nested` flag that `drive_nested` sets; `run_node` passes `!nested`. The AC15 site table also missed `run_consolidate`'s `MapBody::Agent` entirely — flipping that site left the whole workspace green. (2) **The 4 KiB question cap was charged against RUN DATA.** `assemble_prompt` renders every Hard dependency's full output into `## Context` verbatim, so a human-backed node downstream of ANY node that produced ~1000 tokens failed TERMINALLY — after the upstream tokens were spent, unrecoverably (`gate_precheck_by_id` reads the `NodeFailed` back forever), naming three config fields that were not the cause, and defeating the slice's own headline example since a contract is over 4 KiB essentially always. The two halves now get two RULES: the AUTHORED half fails loudly against `MAX_HUMAN_TEXT_BYTES`, the `## Context` half is TRUNCATED per dependency with a visible marker to a new `MAX_HUMAN_CONTEXT_BYTES` (32 KiB). `assemble_prompt` was split into `assemble_prompt_parts` + `render_context_section` to make that possible without a second prompt builder. (3) **A kind-swapped node hung silently and unanswerably.** `run_human_agent` read the SHARED `deadlines` map, so a node already carrying a `SignalAwaited` never took the `NotYetAsking` arm, published no question, and paused forever: `run agent answer` refuses it permanently while `run signal` ACCEPTS a payload and reports exit 0. `run_human_gate` fails loudly on the mirror shape; s3 now does too, keyed on `Fold::prompt_for` (which had been `expect(dead_code)` — the tell). (4) **Two durable plaintext leaks:** the journaled `prompt` was appended unredacted (the one place a credential in a `system_prompt` or skill body reached storage in the clear — `config push` redacts nothing), and `AgentAnswered.actor` reached the journal unredacted while `text` on the same row was scrubbed. (5) **`parse_fm_duration` panicked rather than failing loudly** on a multi-byte unit (`48ℏ`, a byte-index `split_at`) and on an out-of-range magnitude (`999999999999999d`, chrono's infallible constructors) — reachable from `torii config push`, which aborted with a raw backtrace. **Carry-forwards:** no tool use by a human-backed role (SP-4 grants would be gating a PERSON, a different trust question), no multi-turn, no human-as-fallback, no authorization/N-of-M/non-CLI delivery (inherited from s1/s2), and "a human decides whether the loop continues" — the most valuable of the rejected sites — is **slice 4 below**, delivered as a new `GateSpec` variant rather than by making `GateSpec::Agent` polymorphic over the backing (that would reopen exactly what this slice's review closed: legality decided by position, not by caller).
- **slice 4 (`GateSpec::Human` — the human LOOP GATE):** the FOURTH waiting kind, and the one s3's own carry-forward named. A `Loop` whose stop decision a PERSON makes, from an enumerated menu, once per iteration, at the already-reserved `"{loop}/{i}/__gate__"` path. **The menu lives on the GRAPH, in a new `GateSpec::Human { agent, menu }`, and that is the decisive argument for the whole shape:** only a graph-level menu lets `validate_dag` statically reject a menu with no `stops: true` option — a loop that provably cannot converge however the human answers, running to `max_iters` and asking a person that many times to no purpose. On the `AgentDefinition` it would be invisible to validation, and `torii config push` (replace-all) would silently rewrite it. **`stop_when` was rejected outright:** feeding a person's prose to a substring predicate is a live footgun (`TextContains("stop")` matches *"I don't think we should stop yet"*), and against a magic option-name vocabulary `TextContains("halt")` over a menu emitting `"stop"` gives a never-converging loop; `LoopGateOption { name, stops }` says the thing directly. The `AgentRef` still earns its place twice — its `system_prompt` and skills compose the question through the MODEL path's own assembly (the shared `human_question_for` seam, so s3 and s4 cannot drift on what "the agent's prompt" means), and its `backed_by: human { timeout }` is the SLA. **Three new journal variants ⇒ `FORMAT_VERSION` stays 1:** `LoopGateAwaited{node,deadline,prompt,menu}` FIRST-wins (the fourth writer of the shared `deadlines` map), `LoopGateDecided{node,option,actor}` LAST-wins, and **`LoopGateSettled{node,option}`** FIRST-wins. **The Critical this slice shipped and caught is why the third exists:** `run_loop` re-enters `for i in 0..max_iters` from zero on every drive, so iteration 0's gate was re-derived forever against a deadline fixed at the ask — and with expiry read first, the moment wall-clock passed it an ALREADY-HONOURED gate reported `Expired` and killed the whole `Loop`. A 3-iteration loop answered at +30m and +70m under a 1h SLA, each inside its OWN gate's SLA, died at `lp/0/__gate__`; a loop that had already converged was destroyed a day later when a downstream signal woke the run. The drive that honours a decision now records it and every later drive replays THAT — above the clock AND above the SLA read, so a `config push` cannot retroactively kill a loop nobody is waiting on. The ordering is **settled → clock → decision**, never decision-first, which would fix the same symptom and reopen the expiry rule. **Expiry is read BEFORE the decision** (s2's ordering, inverting s3's) because "continue" AUTHORIZES ANOTHER ITERATION OF SPEND, which is an approval; an expired gate fails the `Loop` **whether or not a decision was journaled** — the arm has not read the fold at that point and structurally cannot know, so its message names the DEADLINE and never "no decision". **Zero token spend is STRUCTURAL:** the arm resolves no chain at all, which matters more here than anywhere else in SP-6 because the decision being made *is* whether to spend more. **Operator surface:** `torii run gate decide --node "{loop}/{i}/__gate__" --option <name>` — the same verb a `HumanGate` takes, through ONE resolver (`gate_menu` → `PublishedMenu::{Human,Loop}`), refusing `--note` (the event records none, so it could only be dropped) and refusing a decision at or after the journaled deadline; `run signal` / `run agent answer` refuse it naming both the verb AND the kind; and `run list-paused` renders the FOURTH row shape (`options` and `question` both present), which leaves the listing once the decision is honoured. Four kinds over three verbs. **Whole-slice review — what mattered.** (1) **The reserved `__gate__` SEGMENT was authorable.** s1's rule bans the `/` SEPARATOR, and a `Loop`'s `Subgraph` body is namespaced under `"{loop}/{i}"`, so an inner node named `__gate__` landed on the gate's own path with no separator written. Where the colliding kind COMPLETES rather than waits, nothing wrote the shared `deadlines` map, the gate asked normally, and `LoopGateAwaited` landed at an id already carrying `NodeCompleted` — which torii folds as terminal, so `list-paused` omitted the node and `gate decide` refused it: a run paused on a question no operator surface could show or answer, forever under an indefinite SLA. `plan::feasible` did not cover the planner either, though four places in the slice said it did — its reserved-id walk never recursed. Closed by `validate_dag` block 1c, a recursive `check_reserved_ids`, and an arm-level refusal to ask at a path already carrying `NodeStarted`/`NodeCompleted` (the mid-run `GateSpec::Agent`→`Human` edit no validator can see). (2) **A secret leaked into two durable fields while being scrubbed in a third on the SAME write.** `LoopGateAwaited.menu` was appended straight off the graph and `pause_gate` built `RunPaused.reason` out of the same option names, while `prompt` — which quotes those names back through `gate_ask` — went through the redactor: one author string, clean in one column and plaintext in two, on one append. Option names are author free text out of `torii run submit --graph <file>`, which deserializes and scrubs nothing. Fixed AT the append, so the scrubbed menu is the ONE vocabulary and a later decision keeps resolving journal against journal; `pause_gate` is handed that same copy on both arms and runs the finished reason through the redactor as the write chokepoint (forward-looking only, and its doc says so — handing it the graph's menu again is green). The fix forced a rule nothing else in the slice needed: **a menu whose option names COLLIDE once redacted fails the gate LOUDLY**, because two credential-shaped names collapse to one `[REDACTED]`, `find` takes the first, and an operator picking the only name they were offered gets whichever `stops` came first — a silently inverted decision, the exact outcome §5.3 journals the menu to prevent. `validate_dag` structurally cannot make that check: it is pure over the graph while the `Redactor` is an executor injection, so the same graph would be legal under one executor and not another; it is refused on the authored-cap's reasoning instead (author-controlled config, actionable by whoever wrote it). The append is the last line of defence **for the journal**, which is the precise claim and not a larger one: `Scheduler::submit` calls `store.enqueue` before it drives, so `scheduled_runs.graph` already holds the submitted graph as jsonb in the clear. The journal is the copy that is read BACK — folded by every later drive, printed by `run status`/`run list-paused`, shown to the person, and resolved against by a decision. (3) **The settlement fence was unguarded from both directions** — re-reading the decision in the replay, and folding `LoopGateSettled` LAST-wins, each left the whole crate green. (4) **`fail_loop_gate`'s redaction chokepoint had no test**, while its s3 twin did. (5) **`gate_ask`'s annotation** — the sentence telling a person which option ENDS the run — was pinned only by a `DATABASE_URL`-gated e2e that skips when the variable is unset. (6) **`fail_loop`'s idempotence guard was presence-keyed**, so a `Loop` that failed transiently and later died of a missed human SLA kept the stale cause in the durable record. **Three of the four changes this slice made to paths EVERY graph takes were absent from the spec, which is what the diff is read against; §5.8 now records all four.** `fail_loop`'s message-keyed idempotence is (6) above. `cascade_skip_from` gained the same guard through a new `Fold::skipped` set and an explicit `NodeSkipped` arm in `fold_journal` (previously a `_` catch-all), which changes `NodeSkipped` VOLUME for every node kind and not only a gated `Loop` — a terminally-failed-but-resumable run grew one row per hard dependent per wake, measured 1 / 2 / 3; `RunOutcome.skipped` is deliberately NOT guarded, since the in-process outcome still owes a caller what THIS drive skipped. And s2's `HumanGate` validation now reports a different FIRST error, because extracting the shared `check_menu_option_names` put the empty/empty-name/duplicate rules ahead of the no-`Complete`-option rule — deliberate, since "no Complete option" sends an author hunting for a flag on options that do not exist, and the graph is refused either way with nothing downstream branching on which. The fourth is the reserved-id ban in (1), which refuses graphs that used to validate whatever gate kind they carry. **Carry-forwards:** **free-text reasoning alongside the pick** (the richest version and the natural s5 — it touches the loop's INPUT plumbing, not the gate), **asking once for the whole loop** (a different gate kind, not a variant of this one — it cannot express "continue", which is the decision this slice exists for), no hook for the three loop-gate events (they fall through the `OrchestratorHooks` catch-all exactly as `SignalAwaited`/`GateAwaited`/`AgentAwaited` do — not a regression, and the same observation that a HITL pause is what a live flow-tracking UX most wants), **the human at the other four refused positions** (`MapBody`, `LoopBody`, `Consolidate`, planner — each its own feature, the planner one still the sharpest, since a person would have to hand-author a machine-parseable plan graph), and the standing SP-6 deferrals (authorization, N-of-M, non-CLI delivery, `RunStatus::Rejected`), unchanged and not made worse by this slice. **An untrusted `Expand` planner can author a `GateSpec::Human`** and `feasible` accepts it — not a new capability (a planner could already splice a `HumanGate`), but the right first question for any new node behaviour, and the answer here is yes.

- **SP‑6 — HITL / human‑in‑the‑loop (✅ COMPLETE, all FOUR slices):** ✅ **s1 `AwaitSignal`** — the general primitive: a node that pauses until an external signal arrives, its answer journaled (`SignalReceived`) and folded so a resumed run never re‑asks, with an optional **absolute, journaled** deadline that FAILS the node rather than self‑approving, and `torii run signal <run> --node <node> --payload <json>` as the delivery surface (merged). ✅ **s2 `HumanGate`** — the typed layer over it: a human picks one of an **enumerated menu**, each `GateOption` declaring `Complete` (the decision becomes the node's output) or `Fail` (the node fails and hard‑edge dependents cascade‑skip), with the menu **journaled on `GateAwaited`** so editing the graph cannot retroactively change what an answer meant, the expiry checked BEFORE any decision is read, conditional `Branch` exhaustiveness in `validate_dag`, and `torii run gate approve|reject|decide` + a `list-paused` that shows the menu (merged into `develop` at `a891442`; §3 has the full decision log). Remaining: **human‑as‑Agent** (s3 — a human‑backed agent in the role library whose execution is a pause‑for‑input). **s2 carry‑forwards:** **authorization** (`actor` is attribution, never authentication — it must not be branched on), a distinct **`RunStatus::Rejected`**, and no hook for `GateAwaited`/`GateDecided` either. **Carry‑forwards out of s1:** a **business‑level signal key** distinct from the node id, for an external system that cannot know a node path; **non‑CLI delivery** (webhook/HTTP), which needs the auth model SP‑DATA‑4 deferred; **multi‑party (N‑of‑M) approval and per‑signal authorization** (who may signal what); **`SignalReceived` is uncapped on the DURABLE side** — the 4096‑byte limit is the CLI's, and capping the journal needs the payload to become ref‑or‑inline, a `FORMAT_VERSION` break; **no `OrchestratorHooks` callback fires for `SignalAwaited`/`SignalReceived`** (they fall through the hook catch‑all like `BudgetRaised`/`EffectRecorded`/`MapExpanded`/`MapCompacted` — not a regression, but a HITL pause is exactly what a live flow‑tracking/alerting UX wants, so it is a deliberate deferral); the **terminal re‑`start` empty‑`RunOutcome`** limitation (no `NodeCompleted` is journaled, matching `Branch`/`Subgraph`, so re‑`start`ing an already‑terminal run reports the gate in neither `outputs` nor `completed` — the durable blackboard is unaffected; this is the pre‑existing fresh‑vs‑terminal asymmetry listed under *Perf / correctness follow‑ups* below, not a new one); and **`torii` holds a SECOND, independent fold of `SignalAwaited`** (`cmd/run.rs::signal_states`) duplicating the executor's first‑wins rule — consistent today, but two copies of one rule and only the executor's is mutation‑guarded. - **SP‑7 — prompt budgeting, now THREE slices** (it was booked as one; the split is below). ✅ **SP‑7a window‑aware selection — SHIPPED** (spec + plan dated 2026‑09‑03): the window question moved to selection as the gateway's `ContextWindowGate`, the sixth `AdmissionGate`, registered AFTER `BudgetGate` so every cheaper structural and health skip is still reported ahead of it. It is asked per CANDIDATE against that candidate's own `context_window`, so a heterogeneous `[128k, 8k]` chain now serves a prompt only its larger model can hold — the orchestrator's chain‑minimum `over_budget`/`PromptOverBudget` halt refused that outright and is gone, along with `est_prompt_tokens` and `est_tokens`. An over‑EVERY‑window prompt was still refused rather than truncated — that half held for one slice and SP‑7b ended it, below — but as an `AllGated` naming each candidate's own window, the estimate that exceeded it, and `HumanAction::UseLargerContextWindow` — a remedy distinct from `RaiseBudget`, because no amount of money makes a window bigger. The estimate feeding the gate is a second, deliberately pessimistic one (`estimate_input_tokens_pessimistic`, bytes/3, counting tool SCHEMAS and an assistant turn's `tool_calls` — the ReAct loop's own largest messages carry everything in `tool_calls` and have an EMPTY body) kept separate from the cost estimate because the two gates want opposite biases over one payload. **Which payload kinds are gated is decided in the ESTIMATOR, not the gate:** `Chat` and `Embed` are (an `Embed` batch on its LARGEST text, never the sum — the window bounds one array element, and summing terminally refused 100 RAG chunks an 8k model serves one at a time), while `Stt`/`Tts`/`ImageGenerate`/`VideoGenerate` return 0 and so admit unconditionally, because `context_window` is a chat‑model field those models do not publish. The estimator matches on the `Payload`, which is what goes on the wire; `Capability` has eleven variants over six payload kinds and does not map cleanly (`ImageAnalyze` is a `Chat` payload and must be gated like one). **The boundary that made this an unbudgeted‑run benefit only — CLOSED by the SP‑7a follow‑on (spec `2026-09-04-sp-7a-serving-window-bound-design.md`).** For one day the SP‑DATA‑5 clamp bounded `max_tokens` by `min_context_window(chain) − est` BEFORE selection, so on the `[128k, 8k]` example it computed `8192 − 20000`, saturated to 0, fell under `MIN_OUTPUT_TOKENS` and refused inside the orchestrator — the gate never ran and a budgeted run got the old failure with a budget‑flavoured message. The clamp now bounds by `Gateway::min_serving_context_window(chain, est) − est`: the smallest window among the models that can actually HOLD the request, which is exactly the set the gate admits, so the minimum over it is safe for whichever candidate wins without knowing which — and, every member satisfying `window >= est`, it cannot saturate to zero the way the chain minimum did. When NOTHING can serve the request the accessor answers `None`, the clamp contributes no window term at all, and the refusal is handed to the gate: a budgeted over‑every‑window prompt now gets the same per‑candidate `AllGated` diagnosis an unbudgeted one always did, rather than a durable budget pause naming a cap raise that cannot help. **For one commit that handover made the run TERMINAL, and review reversed risk M1 to fix it (2026‑09‑04):** nothing revives a failed run — `force_wake` matches `status = 'paused'`, `torii run wake` says "not queued", `submit` refuses a used id — so a run's memos and spend were reachable only by hand SQL. `classify_gateway_error` now treats an `AllGated { resume_after: None }` that carries a `human_action` as the indefinite HOTL pause (never auto‑woken; cleared by `force_wake` once the operator has widened the chain), failing only when neither a deadline nor an action is present. The fix is not window‑specific — an auth lockout or a capability gate produced the same unrecoverable terminal state. **The follow-on's own whole‑slice review then found the bound resting on a premise that did not hold, and it is fixed in the same spec (§4.1).** "Exactly the set the gate admits" is a claim about ONE `est`, and the two halves computed two: the clamp had its own estimator applying `ceil` PER STRING over characters, the gate takes `ceil(Σ bytes / 3)` once, and on ASCII the clamp's figure is the LARGER one — so its serving set was a strict SUBSET of the set selection drew from. Reproduced end to end both ways: an empty clamp set against a non‑empty gate set dropped the window term entirely and dispatched `max_tokens` bounded only by the output limit (`3800 + 1024` against a 4096 window), and a set missing the small candidate the gate keeps bounded by a 200 000 window and sent that figure to `small`. Both are the `prompt + max_tokens > context_window` provider 400 the window term exists to prevent, arriving as a terminal `NodeFailed` on a budgeted run where the identical UNBUDGETED call succeeds — strictly worse than the recoverable pause the pre‑follow‑on code gave. Closed structurally rather than by agreement: `estimate_input_tokens_pessimistic` is `pub`, the clamp calls it on the very `Payload` it dispatches, and the orchestrator's two rival estimators (`dispatch::est_input_tokens` and `agent::prompt::est_tokens_pessimistic`) are DELETED — the orchestrator now holds no token estimator at all. Aligning the two formulas by hand was rejected because the drift ran the OTHER way on multi‑byte text, so neither figure bounded the other and no slack constant could cover it. Bounding by the SELECTED candidate is still strictly more precise and is still the clamp spec's §8 item — it needs the run's budget plumbed into the gateway. ✅ **SP‑7b context budgeting — SHIPPED** (spec + plan dated 2026‑09‑04): an agent turn whose prompt exceeds EVERY candidate's window is now DEGRADED and dispatched instead of refused. A pure planner (`plan_budget`) turns `Gateway::max_context_window(chain)` — the only accessor there that folds `max`, and safe because it does not decide admission, the per‑candidate gate still does — into a byte budget for the `system` half (`3 × (window − MIN_OUTPUT_TOKENS − transcript)`, where the `× 3` is EXACT rather than a fudge because the gateway's pessimistic estimator is `ceil(bytes/3)`), drops whole tool schemas from the END of the activation order to make room (whole, because a schema truncated mid‑JSON is a provider 400 — a degradation turned into a hard failure), and the existing human‑path truncator applies it. **The crux is what is JOURNALED: the budget INTEGER, not the cut.** Everything else feeding the cut is already replay‑stable (context from CAS by digest, `authored` and tool activation from the pinned registry), and this integer was the only unfenced input, because it derives from a model's `context_window` and `GatewayConfig` carries NO version field — so an operator edit is invisible to the config fence. `ContextBudgeted{budget_bytes,…}` is appended BEFORE dispatch and folded **FIRST‑wins**, which makes the cut a function of journaled state on drive 1 as well as on resume; without it a window edit between drives re‑cuts a turn already memoized, `agent_input_hash` stops matching, and `DeterminismViolation` leaves the run terminally `Failed` where `force_wake` cannot revive it — the same unrecoverable class the M1 reversal was done to remove. The **un‑budgeted** turn is fenced too, by `memo.contains(eid) && !budgets.contains(eid)`, since AC11 makes an in‑window turn journal nothing and absence alone cannot tell "fits" from "not budgeted yet". **The floor:** a cut retaining under `CONTEXT_FLOOR_FRACTION` (0.25, a judgment call whose doc says so and names the operator `warn` as the instrument that will replace it with a measurement) is refused — as the durable HOTL pause, never a terminal failure — and the refusal is SP‑7b's ONLY when a cut that FITS exists and retains too little; when no cut can fit (the `authored` half alone overruns, and it is never cut) the un‑cut prompt goes to the gate for its strictly better per‑candidate diagnosis. **Not silent:** four disclosure channels — the per‑entry truncation marker and the `(N of M dependencies shown)` tail (two signals for two different degradations — TRUNCATED entries and DROPPED ones — and a turn exhibits either or BOTH, the both‑case being the ordinary way the tail is reached at all, since what normally pushes a section past its budget is a marker's own overrun on an entry that therefore carries one), the `ContextBudgeted` row, an ADDITIVE `context_budgeted: true` output key (so an unmodified `BranchCond::TextContains` consumes a degraded answer exactly as before), and a `warn`.
