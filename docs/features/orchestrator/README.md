# Orchestrator

The agentic execution framework that wraps the gateway: a hierarchical,
runtime-expandable graph of agents on a durable step-journal, resumable without
re-spending tokens and with no silent failures. Full design in
[`../../superpowers/specs/2026-08-06-sensei-orchestrator-design.md`](../../superpowers/specs/2026-08-06-sensei-orchestrator-design.md).

## Notes

- New crates in this workspace: `orchestrator-core` (types/traits), `orchestrator` (engine), `orchestrator-store` (adapters — in-memory + the SP-DATA-1 Postgres backend behind a `postgres` feature; dbd schema in `gateway/database/`), and `torii` (SP-DATA-4 — the operator control plane, and the workspace's **first binary**; a lib+bin pair so its commands are callable from tests).
- Walking-skeleton first slice = a deep-research mini (design §17). First *implementation* slice overall is gateway [routing](../routing/README.md) SP-0.
- **Persistence (SP-DATA):** durable run state (journal + CAS + context in Postgres) landed in SP-DATA-1; **`PostgresConfigSource` + durable `config_versions` (the cross-process config-version fence)** in SP-DATA-2; the **durable scheduler** (`Scheduler` + `scheduled_runs` `SchedulerStore` — wakes a paused run at its `resume_after` cross-process, exactly-once, + observe/intervene) in SP-DATA-3; and **`torii`, the management CLI** (the first production `tick()` caller, two boot tiers, honest observe/intervene reporting, and the durable config write path — which closed SP-DATA-2's two carry-forwards with the atomic `load_versioned()` read and the bump-first `store_and_bump()` write) in SP-DATA-4; and the **per-run token budget** (the journal as a durable spend ledger — `EffectRecorded{usage}` + `RunStarted{budget}` + `BudgetRaised`, folded **by effect id** so a duplicate record cannot double-count on resume; one metered-dispatch chokepoint gating all four model-call producers; exhaustion → the HOTL pause class; `torii run submit|status|wake --budget-tokens`) in SP-DATA-5 — see the [overview decision log](../../superpowers/orchestrator-overview.md#3-decision-log-asked--confirmed). **SP-DATA is COMPLETE (all five slices).** Known edges left open: `LlmPlannerSelector::select` is a fifth, unbudgeted and unledgerable model-call site, and a gated `Map` fan-out journals one `RunPaused` per gated child.
- **HITL (SP-6):** ✅ **s1 `AwaitSignal`** — a node that pauses until an external signal arrives. SP-DATA-4 shipped human *on* the loop (`cancel`/`wake` intervene from outside; `force_wake` is a RESUME, not a DECISION); this is human *in* the loop — the graph blocks on a human decision as a first-class node, and `torii run signal <run> --node <node> --payload <json>` carries the ANSWER back in (journaled, redacted before the write, capped at 4 KiB **as the redacted row is written** — redaction replaces a secret shape with the longer `[REDACTED]`, so it can grow a payload past the cap — then `force_wake`d; `run list-paused` names every awaiting node and its deadline). It reports the effect it ACHIEVED, ordered by journal `Seq`: an answer that a drive already in flight read and completed the node with is `signalled` (exit 0), an answer that landed after the node had already terminated is reported as **journaled durably but unread** (exit 2) rather than "not delivered", and a terminal run is told to start a new one instead of to wait for a pause that never comes. The **absolute deadline is journaled, never recomputed** — recomputing `now + timeout` per execution would push it forward on every resume, so a repeatedly-woken run would never expire — and a fired deadline **fails** the node rather than self-approving. ✅ **s2 `HumanGate`** — the TYPED layer over s1: a human picks one of an enumerated menu and each `GateOption` declares its own outcome (`Complete` flows on, `Fail` fails the node and cascade-skips hard-edge dependents), so a rejection has real semantics instead of being a value the author must remember to test for. **The menu is DURABLE** — `GateAwaited{node,deadline,options}` journals what the human was actually shown, so editing the graph cannot retroactively change what their answer meant — and `GateDecided{node,option,actor,note}` carries the answer (both new variants ⇒ `FORMAT_VERSION` stays 1; decisions fold LAST-wins, menus FIRST-wins). The waiting machinery is **shared with s1, not copied** (`gate_precheck`/`wait_or_expire`/`pause_awaiting`), since s1's review found real defects in exactly those arms. **The deadline is checked BEFORE any decision is read**, so a decision cannot approve a gate whose SLA ran out — the accepted cost being that a decision delivered in time is discarded if no drive folds it before the deadline. `validate_dag` rejects an empty menu, empty or duplicate option names and a menu with no `Complete` option, and adds **conditional exhaustiveness**: a `Branch` switching on a gate must arm every `Complete` option and may name no undeclared one (`Fail` options exempt; a gate with no `Branch` is legal). Operator surface: `torii run gate approve|reject|decide` (which validates the option and the deadline against the JOURNAL before appending anything, then force-wakes) and `run list-paused`, which renders each gate's menu. **`actor` is ATTRIBUTION, not AUTHENTICATION** — it is whatever string the caller supplied, so it must not be branched on as an access control. **human-as-Agent (s3) is the remaining slice**; see the [overview decision log](../../superpowers/orchestrator-overview.md#3-decision-log-asked--confirmed) for the full carry-forward list (no hook fires for either signal or gate event; the durable side of `SignalReceived` is uncapped; a terminal re-`start` reports the gate in neither `outputs` nor `completed`).
