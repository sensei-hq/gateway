# Orchestrator

The agentic execution framework that wraps the gateway: a hierarchical,
runtime-expandable graph of agents on a durable step-journal, resumable without
re-spending tokens and with no silent failures. Full design in
[`../../superpowers/specs/2026-08-06-sensei-orchestrator-design.md`](../../superpowers/specs/2026-08-06-sensei-orchestrator-design.md).

## Notes

- New crates in this workspace: `orchestrator-core` (types/traits), `orchestrator` (engine), `orchestrator-store` (adapters — in-memory + the SP-DATA-1 Postgres backend behind a `postgres` feature; dbd schema in `gateway/database/`), and `torii` (SP-DATA-4 — the operator control plane, and the workspace's **first binary**; a lib+bin pair so its commands are callable from tests).
- Walking-skeleton first slice = a deep-research mini (design §17). First *implementation* slice overall is gateway [routing](../routing/README.md) SP-0.
- **Persistence (SP-DATA):** durable run state (journal + CAS + context in Postgres) landed in SP-DATA-1; **`PostgresConfigSource` + durable `config_versions` (the cross-process config-version fence)** in SP-DATA-2; the **durable scheduler** (`Scheduler` + `scheduled_runs` `SchedulerStore` — wakes a paused run at its `resume_after` cross-process, exactly-once, + observe/intervene) in SP-DATA-3; and **`torii`, the management CLI** (the first production `tick()` caller, two boot tiers, honest observe/intervene reporting, and the durable config write path — which closed SP-DATA-2's two carry-forwards with the atomic `load_versioned()` read and the bump-first `store_and_bump()` write) in SP-DATA-4; and the **per-run token budget** (the journal as a durable spend ledger — `EffectRecorded{usage}` + `RunStarted{budget}` + `BudgetRaised`, folded **by effect id** so a duplicate record cannot double-count on resume; one metered-dispatch chokepoint gating all five model-call producers; exhaustion → the HOTL pause class; `torii run submit|status|wake --budget-tokens`) in SP-DATA-5 — see the [overview decision log](../../superpowers/orchestrator-overview.md#3-decision-log-asked--confirmed). **SP-DATA is COMPLETE (all five slices).** Its two budget carry-forwards are closed too: `Snapshot` now carries `spent` + `budget`, and `LlmPlannerSelector::select` — a fifth model-call site the budget could neither gate nor ledger, because it held its own gateway — now reaches a provider only through a `ModelDispatch` capability the executor lends it, so its spend is gated, metered and journaled under a reserved `"{expand}/__select__"` path like every other producer. Known edge still open: a gated `Map` fan-out journals one `RunPaused` per gated child. **The budget CLAMP follow-on** then shrank that "at most one call" overshoot: a budgeted `Chat` request now carries `max_tokens = min(remaining − a pessimistic input estimate, the chain's smallest `max_output_tokens`, `min_serving_context_window(chain, est) − est`, the caller's own)` — that third term being the smallest window that can actually HOLD the request rather than the chain-wide minimum, so a `[128k, 8k]` chain serves a 20k prompt on the large model instead of being refused before the gateway is asked, and an empty serving set contributes no term at all because the [`ContextWindowGate`](../routing/README.md) owns that refusal, so the provider enforces the cap instead of our arithmetic. What remains is the INPUT-estimate error — **bounded and biased toward refusing early, NOT eliminated**. The half a debugger needs: **a budgeted run can now pause with `spent < cap`**, even at `spent == 0`, because an allowance below `MIN_OUTPUT_TOKENS` (256) is refused rather than spent on a reply that would arrive truncated; the pause names the headroom the cap must clear, and `torii run submit|wake --budget-tokens` rejects a cap under the floor outright.
- **HITL (SP-6):** ✅ **s1 `AwaitSignal`** — a node that pauses until an external signal arrives. SP-DATA-4 shipped human *on* the loop (`cancel`/`wake` intervene from outside; `force_wake` is a RESUME, not a DECISION); this is human *in* the loop — the graph blocks on a human decision as a first-class node, and `torii run signal <run> --node <node> --payload <json>` carries the ANSWER back in (journaled, redacted before the write, capped at 4 KiB **as the redacted row is written** — redaction replaces a secret shape with the longer `[REDACTED]`, so it can grow a payload past the cap — then `force_wake`d; `run list-paused` names every awaiting node and its deadline). It reports the effect it ACHIEVED, ordered by journal `Seq`: an answer that a drive already in flight read and completed the node with is `signalled` (exit 0), an answer that landed after the node had already terminated is reported as **journaled durably but unread** (exit 2) rather than "not delivered", and a terminal run is told to start a new one instead of to wait for a pause that never comes. The **absolute deadline is journaled, never recomputed** — recomputing `now + timeout` per execution would push it forward on every resume, so a repeatedly-woken run would never expire — and a fired deadline **fails** the node rather than self-approving. ✅ **s2 `HumanGate`** — the TYPED layer over s1: a human picks one of an enumerated menu and each `GateOption` declares its own outcome (`Complete` flows on, `Fail` fails the node and cascade-skips hard-edge dependents), so a rejection has real semantics instead of being a value the author must remember to test for. **The menu is DURABLE** — `GateAwaited{node,deadline,options}` journals what the human was actually shown, so editing the graph cannot retroactively change what their answer meant — and `GateDecided{node,option,actor,note}` carries the answer (both new variants ⇒ `FORMAT_VERSION` stays 1; decisions fold LAST-wins, menus FIRST-wins). The waiting machinery is **shared with s1, not copied** (`gate_precheck`/`wait_or_expire`/`pause_awaiting`), since s1's review found real defects in exactly those arms. **The deadline is checked BEFORE any decision is read**, so a decision cannot approve a gate whose SLA ran out — the accepted cost being that a decision delivered in time is discarded if no drive folds it before the deadline. `validate_dag` rejects an empty menu, empty or duplicate option names and a menu with no `Complete` option, and adds **conditional exhaustiveness**: a `Branch` switching on a gate must arm every `Complete` option and may name no undeclared one (`Fail` options exempt; a gate with no `Branch` is legal). Operator surface: `torii run gate approve|reject|decide` (which validates the option and the deadline against the JOURNAL before appending anything, then force-wakes) and `run list-paused`, which renders each gate's menu. **`actor` is ATTRIBUTION, not AUTHENTICATION** — it is whatever string the caller supplied, so it must not be branched on as an access control. ✅ **s3 human-as-Agent** — the third waiting kind (s3 called it the last; s4's loop gate is the fourth), and the one that is a REGISTRY fact rather than a graph one: `AgentBacking::{Model, Human{timeout}}` on `AgentDefinition` (serde-defaulted to `Model`, so every existing agent md and every `config_agents` jsonb row is byte-identical), authored as `backed_by: human` + `timeout: 48h` in frontmatter. A `NodeKind::Agent` whose `AgentRef` resolves to a human-backed role short-circuits **before `resolve_chain`**, so zero token spend is STRUCTURAL, not measured — it pauses once, journals `AgentAwaited{node,deadline,prompt}`, and completes from `AgentAnswered{node,text,actor}` with output `{"text","actor"}` under the SAME `"text"` key a model-backed agent produces, so an unmodified `BranchCond::TextContains` consumes a human's answer without knowing it was human. **The answer is read BEFORE expiry** — a deliberate divergence from s2, because an agent's answer is WORK PRODUCT, not an approval, so there is nothing to self-approve and discarding an in-time answer because a worker was down punishes the human for infrastructure; a fired expiry is still terminal. **Legal ONLY as a top-level `Agent` node**, enforced at RUNTIME (`validate_dag` cannot see the registry) and by node POSITION rather than by calling function — the whole-slice review found the rule keyed on the caller, so a one-node `Subgraph` wrapper bypassed it and delivered the unbuilt "a human re-answers every `Loop` iteration" feature. **The journaled question is bounded by two rules, not one:** the AUTHORED half (system prompt + activated skills + the node input) fails loudly over `MAX_HUMAN_TEXT_BYTES`, while the `## Context` half is RUN DATA and is TRUNCATED to `MAX_HUMAN_CONTEXT_BYTES` with a visible marker — charging one cap against both made an ordinary verbose upstream kill the node terminally after its tokens were already spent. Operator surface: `torii run agent answer <run> --node <id> (--text|--text-file) [--as who]`, three-way cross-refusal against `run signal` and `run gate decide`, and `run list-paused` showing the question. Carry-forwards: no tool use by a human-backed role, no multi-turn, no human-as-fallback. (s3's own carry-forward — "a human decides whether the loop continues" — is **s4 below**, and it landed as a new `GateSpec` variant rather than through `GateSpec::Agent`: a human backing there is still refused, deliberately, so legality stays decided by position and not by caller.) ✅ **s4 `GateSpec::Human` — the human LOOP GATE**, the FOURTH waiting kind: a `Loop` whose stop decision is made by a person picking from an enumerated menu, once per iteration, at the reserved `"{loop}/{i}/__gate__"` path. **The menu lives on the GRAPH, not the registry**, and that is the decisive argument for the whole shape: only a graph-level menu lets `validate_dag` statically reject a menu with no `stops: true` option — a loop that provably cannot converge however the human answers, running to `max_iters` and asking a person that many times to no purpose. (On the `AgentDefinition` it would be invisible to validation and `torii config push`, which is replace-all, would silently rewrite it.) There is deliberately **no `stop_when` predicate**: feeding a person's prose to `TextContains("stop")` matches *"I don't think we should stop yet"*, so `LoopGateOption { name, stops }` says the thing directly. **Three new journal variants** ⇒ `FORMAT_VERSION` stays 1: `LoopGateAwaited{node,deadline,prompt,menu}` FIRST-wins (the durable menu and question, both redacted before the append — and a menu whose names COLLIDE once redacted fails the gate loudly rather than offering two options under one name), `LoopGateDecided{node,option,actor}` LAST-wins, and **`LoopGateSettled{node,option}`** FIRST-wins. The third exists because of the Critical this slice shipped and caught: `run_loop` re-enters `for i in 0..max_iters` from zero on every drive, so iteration 0's gate was re-derived forever against a deadline fixed at the ask — and with expiry read first, the moment wall-clock passed it an ALREADY-HONOURED gate reported `Expired` and killed the whole `Loop`, destroying loops that had converged hours earlier. The drive that honours a decision now records it and every later drive replays THAT, above the clock and above the SLA read; the settlement is also the line after which `LoopGateDecided`'s LAST-wins correction no longer moves a convergence point already spent against. **Expiry is read BEFORE the decision** — s2's ordering, inverting s3's — because "continue" AUTHORIZES ANOTHER ITERATION OF SPEND, which is an approval; an expired gate fails the `Loop` **whether or not a decision was journaled** (the arm has not read the fold and cannot know, so its message names the DEADLINE). Zero token spend is STRUCTURAL: the arm resolves no chain at all, which matters more here than anywhere else in SP-6 because the decision being made *is* whether to spend more. Operator surface: `torii run gate decide --node "{loop}/{i}/__gate__" --option <name>` (the same verb a `HumanGate` takes — one resolver, `gate_menu`, returns a `PublishedMenu::{Human,Loop}`; `--note` is REFUSED because the event records none; a decision at or after the journaled deadline is refused), `run signal`/`run agent answer` each refusing it by verb AND kind, and `run list-paused` rendering it as the FOURTH row shape (`options` and `question` both present), which leaves the listing once the decision is honoured. Four kinds over three verbs. **Whole-slice review** additionally closed the reserved `__gate__` SEGMENT — authorable inside a `Loop`'s `Subgraph` body, where it namespaces onto the gate's own path; with a colliding node kind that COMPLETES the run paused on a question `list-paused` omitted and `gate decide` refused, forever under an indefinite SLA. Carry-forwards: **free-text reasoning alongside the pick** (the richest version, and the natural s5 — it touches the loop's input plumbing), **asking once for the whole loop** (a different gate kind, not a variant of this one), and no hook for the three loop-gate events. See the [overview decision log](../../superpowers/orchestrator-overview.md#3-decision-log-asked--confirmed) for the full carry-forward list (no hook fires for any signal, gate or loop-gate event; the durable side of `SignalReceived` is uncapped; a terminal re-`start` reports a waiting node in neither `outputs` nor `completed`).
